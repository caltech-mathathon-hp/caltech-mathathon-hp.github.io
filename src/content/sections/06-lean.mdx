## Why a computer checks it

A reduction proof is long and full of cases, and a reader checks many of them by looking at
pictures. In [our audit](../original-proof/#our-audit-notes) of Berger and Leighton's proof we
found a footnote that is false as written, and several steps that the paper leaves to the reader.

In Lean a proof is a program, and Lean accepts it only if every step follows from the definitions
by the rules of logic. We call a statement **proved in Lean** when

- the Lean project builds;
- no `sorry` is left in its proof or in anything the proof uses (`sorry` stands for a step that is not proved yet);
- it rests only on Lean's three standard axioms, `propext`, `Classical.choice` and `Quot.sound`, as `#print axioms` shows;
- it does not use `native_decide`, which runs compiled code instead of checking a proof.

We found no earlier machine-checked proof that HP folding is hard, in any proof assistant. The
only Lean library for the HP model, by <Cite k="kjoshanssen2024ptyche" />, defines folds and
bounds their number of contacts, but proves nothing about hardness.

## What Lean proves

<Theorem kind="Theorem" source="Berger & Leighton 1998" status="lean">
If SAT is NP-hard, then HP folding on the cubic lattice is NP-complete, and so is perfect folding.
</Theorem>

Both certificates prove this theorem, and about the same statements. The definitions and the two
final statements are written once, in the team's library, and our project builds on a copy of that
library without changing it. So the two proofs share every step but one.

Lean follows the plan of the paper. Perfect folding asks whether a string with $n^3$ H's has a
fold whose H's fill an $n \times n \times n$ cube. Theorem 3.2 of the paper says that this happens
exactly when the string has a fold with $3n^2(n-1)$ pairs of H's on neighbouring sites, the most
that $n^3$ sites can have. So perfect folding is HP folding with a particular threshold. Lean
proves Theorem 3.2 with no assumption.
It also proves, with no assumption, that both problems are in NP: it builds a Turing machine that
checks a proposed fold in polynomial time.

For hardness, Lean follows the chains at the top of this page. Each step is a reduction: a
function that turns instances of one problem into instances of the next, preserves the answer,
and is computed by a Turing machine whose running time Lean proves polynomial. The first step,
from every problem in NP to SAT, is the Cook–Levin theorem; the next section explains how its
proof enters. These are the main results as Lean states them; their proofs are in the
files linked below each block.

## The Cook–Levin step

The Cook–Levin theorem says that every problem in NP reduces to SAT in polynomial time. Cook
proved it in 1971 and Levin, independently, in 1973. It has been checked by computer in Coq
<Cite k="gaher2021mechanising" /> and in Isabelle <Cite k="balbach2023cook" />, but not in
mathlib, Lean's main library, because a proof has to write a whole run of a Turing machine as a
formula, a long project of its own. A Lean 4 proof by <Cite k="rbarish2026npcompleteness" />
exists, but it uses its own Turing machines instead of mathlib's, so connecting it to the team's
project would take more work, and no person has reviewed it.

So the team's reduction, in `lean/cubic`, states Cook–Levin as a proposition, `SAT.CookLevin`, and
its three hardness theorems take it as a hypothesis `hCL`. A hypothesis is not an axiom: Lean checks that the
theorem follows from it, and a Lean proof of `SAT.CookLevin` turns the three theorems into
unconditional ones.

<LeanCode names="SAT.CookLevin" caption="The hypothesis: SAT is NP-hard" />

`#print axioms` lists the axioms a theorem rests on, but not its hypotheses, so `hCL` shows only
in the theorem's type. This is what Lean prints for three of the main results:

### A Lean proof of Cook–Levin

The team has since proved it, in the folder `lean/cooklevin`. The proof is written for the
team's definitions. It shares 67 files with the team's library, among them `CookLevin.lean` and
`Complexity.lean`, which define SAT, NP and reductions, and all 67 are byte-identical to the
team's. So its theorem has exactly the type of the hypothesis `hCL`.

<LeanCode cert="cooklevin" names="SAT.CookLevinUniversal.cookLevin SAT.CookLevinUniversal.inNP_karp" caption="Cook–Levin: SAT is NP-hard, because every problem in NP reduces to it" />

The proof is Cook's. Take a problem in NP and its verifier, a mathlib Turing machine that checks
a certificate in polynomial time. Write a run of the verifier as a table with one row per step.
The table is a correct run exactly when every small window of it obeys local rules, and a CNF
formula can state these rules, so the formula is satisfiable exactly when some certificate makes
the verifier accept. Most of the proof is the other half: Turing machines that write this formula
out, with proofs of what they write and that they run in polynomial time. A last machine rewrites
the formula with at most three literals per clause, so 3-SAT is NP-hard as well. The project's
<a href={cooklevin.links.docs.readme}>README</a> lists its files step by step.

## The definitions

Lean checks every step after the definitions, but not the definitions themselves. If a definition
said something other than what the paper means, Lean would prove a different theorem. Both
certificates use these definitions, so we show them once, in full, to compare with the [front page](../) and with the paper. The
<a href={lean.links.docs.model}>model notes</a> list every choice they make, down to empty strings
and how numbers are written.

Two choices need a comment. First, the project counts every pair of H's on neighbouring sites,
including H's that are neighbours on the string, as the paper does; the paper calls them bonds.
The front page counts only pairs that are not neighbours on the string. The two counts differ by
the number of HH pairs next to each other in the string, which depends only on the string, so
both counts give the same folding problem.

Second, mathlib has Turing machines with a polynomial running time, but no class NP and no
reductions <Cite k="mathlib2026computability" />. The project defines them on top of mathlib's
machines. A problem is in NP when a polynomial-time machine can check a certificate of polynomial
length, a reduction is a function computed by a polynomial-time machine that preserves the
answer, and a problem is NP-hard when every problem in NP reduces to it.

## Two proofs of one step

Both chains go from SAT to bin packing by the team's reduction, and from perfect folding to HP
folding by the team's reduction. They differ in the step between, from bin packing to perfect
folding, where each builds its own string.

### Berger and Leighton's string

The team's certificate proves the paper's theorem about the paper's problems, but in two places
not by the paper's argument. The paper takes the hardness of bin packing with small numbers from
Garey and Johnson <Cite k="garey1979computers" />. The project proves it in Lean instead, from SAT
through 3D matching, and Cook–Levin is proved in Lean too, so no published result enters the proof. Our certificate
uses this part of the team's proof as it is.

The reduction from bin packing to perfect folding builds a different string from the one in the
paper's Figure 3, so the paper's Lemmas 3.3 to 3.8 are not formalized one by one. Lean proves
both directions for the new string: it has a perfect fold exactly when the items fit. The
<a href={lean.links.docs.proofRoute}>proof route</a> describes the construction.

### Our string

Our certificate formalizes the version of [our proof](../one-edge-proof/) that the
[3D view](../one-edge-proof/#folding-a-small-instance) on that page folds. The bins are gaps on
one edge of the cube, the shelf. Separators, each a single H, cut the shelf into gaps, and two
tethers pin the first and the last separator to the two ends of the shelf, so every gap is
exactly full.

Take bin packing with sizes $a_1, \dots, a_k$, $m$ bins and capacity $B$. The reduction first
multiplies every size and $B$ by 6, and if $m$ is even it adds one bin and one item of size $B$.
Then it writes a string $S$ with $n^3$ H's, where $n = m(B+1)+3$. Lean proves both directions:
a perfect fold of $S$ gives a packing, and from a packing it builds a perfect fold of $S$, site
by site. It also builds a Turing machine that writes $S$ and proves that it runs in polynomial
time. On the instances that the 3D view offers, Lean computes the same side of the cube and the
same number of H's as the view shows (`checks/SmallInstances.lean`).

<LeanCode cert="shelf" names="Shelf.reductionCorrect Shelf.shelfKarp" caption="Our reduction: correct on every input, and computed in polynomial time" />

As in the team's project, a machine gets any input. So the reduction first checks that the sizes
are positive and add up to $mB$, and sends any other input to a string with no perfect fold. The
team's source problem also asks that every size is even, and our reduction makes the same check.
Our <a href={shelf.links.docs.proofRoute}>proof route</a> lists the other places where Lean
differs from our write-up.

## Check it yourself

You need [elan](https://github.com/leanprover/elan), Lean's installer, which fetches the right
version of Lean by itself. Download a project with the button on its card and unpack it. The
team's project:

<LeanCommands step="zip" />

Our project:

<LeanCommands cert="shelf" step="zip" />

The Cook–Levin project has no card; <a href={asset(cooklevin.download.path)} download>download it
here</a> (zip, {size(cooklevin.download.bytes)}), then:

<LeanCommands cert="cooklevin" step="zip" />

The three projects are also in the website's repository on GitHub, ours in `lean/shelf` and the
Cook–Levin proof in `lean/cooklevin`, next to the team's. To clone it and go to the team's
project:

<LeanCommands step="git" />

In each folder, download mathlib's compiled files, build the project and print the main results
with their axioms. Only the last command differs. For the team's project:

<LeanCommands step="build" />

For ours:

<LeanCommands cert="shelf" step="build" />

In ours, `lake env lean checks/SmallInstances.lean` also recomputes the sizes that the 3D view
shows, and prints nothing when they agree.

For the Cook–Levin project:

<LeanCommands cert="cooklevin" step="build" />

The first command downloads several gigabytes, and the build checks every proof in the project.
Ours also builds the team's library and the Cook–Levin proof from its copy, which takes a few more
minutes. For the team's
full audit, install PowerShell 7 and run the script below. It compares every file with its
recorded hash, searches the code for forbidden commands, and prints the axioms of every public
declaration.

<LeanCommands step="verify" />

On every change GitHub builds the three projects again, checks the axioms of their main
results and runs the team's full audit; <a href={lean.links.ci}>here are the runs</a>. The team's zip holds the version of
{date(lean.source.date)}, commit <code>{lean.source.commit?.slice(0, 7)}</code>, and its SHA-256 is
<code class="ln-hash">{lean.download.sha256}</code>. Ours holds the version of
{date(shelf.source.date)}, commit <code>{shelf.source.commit?.slice(0, 7)}</code>, and its SHA-256
